# Writing a migration

Schema changes in this repo are raw SQL. Alembic is a runner only.

**Never run `alembic revision --autogenerate`.** It is used in CI as a drift
detector, never as a generator.

Every schema change produces three things in the same commit:

1. the `.up.sql` and `.down.sql` pair
2. the Alembic revision that runs them
3. the matching edit to the Orm class in `libs/database/orm/`

Missing the third is the most common failure — the code and the database silently
diverge until CI's drift check catches it.

## Layout

```
backend/migrations/
├── migration_runner.py
├── revisions/
│   └── 20260912_1423_create_pb_user.py
└── sql/
    └── pb_user/                      # one folder per table, named exactly as the table
        ├── 0001_create_pb_user.up.sql
        └── 0001_create_pb_user.down.sql
```

- SQL files: `<nnnn>_<what_it_does>.<up|down>.sql`, zero-padded to four, in the
  folder for the table they change. The verb describes the change:
  `create_pb_user`, `add_display_name`, `backfill_persona_slug`, `drop_legacy_token`.
- The numeric prefix orders changes within one table's folder, for human reading.
  Real ordering is Alembic's `down_revision` chain.
- Revision files: `<YYYYMMDD>_<HHMM>_<slug>.py`, generated by `alembic revision` via
  `file_template` in `alembic.ini`.
- A change spanning two tables still gets one revision; put each table's SQL in its
  own folder and have the revision run both files in dependency order.

## Naming

Every object a migration creates is prefixed `pb_`: tables (`pb_user`), enum types
(`pb_text_type`), and sequences. Constraint and index names start with their table
name, so they carry the prefix too: `pb_user_pkey`, `pb_user_email_key`,
`pb_persona_user_id_idx`. Postgres's generated names already follow this pattern; a
name you write by hand must as well. Alembic's own `alembic_version` table keeps its
default name.

Table names are singular: `pb_user`, `pb_persona`. A many-to-many table joins both
singular names: `pb_persona_tag`.

## Steps

1. **Find the current head** — `alembic heads`, or the revision with no child in
   `revisions/`. The new revision's `down_revision` points at it. The chain is
   append-only; never insert a revision between two that have already run.
2. **Write the `.up.sql`.** One logical change per file.
3. **Write the `.down.sql`.** Always. If the change is irreversible (dropping a
   column holding data), the file carries a comment saying so plus whatever
   schema-only reversal it can manage. Never omit it.
4. **Write the revision wrapper** (see below).
5. **Update the Orm class** in `libs/database/orm/` to match.
6. **Stop.** Report what you wrote and let Tyler run it. Do not run `alembic upgrade`.

## Revision wrapper

The wrapper contains no SQL — it names files and nothing else.

```python
# revisions/20260912_1423_create_pb_user.py
from migration_runner import MigrationRunner

revision = "20260912_1423"
down_revision = "20260908_1102"

MIGRATION_RUNNER = MigrationRunner()


def upgrade() -> None:
    MIGRATION_RUNNER.run_transactional("pb_user/0001_create_pb_user.up.sql")


def downgrade() -> None:
    MIGRATION_RUNNER.run_transactional("pb_user/0001_create_pb_user.down.sql")
```

## Transactional vs non-transactional

`MigrationRunner` exposes two methods. Pick deliberately.

**`run_transactional(path)`** — the default. Splits the file with `sqlparse` and
executes every statement inside the migration's transaction. Use for anything that
can run in a transaction, which in Postgres is nearly everything including DDL.

**`run_non_transactional(path)`** — opens an `autocommit_block()` and executes the
file. It raises if the file contains more than one statement, because a partial
failure outside a transaction leaves the schema half-changed with nothing to roll
back.

Use it only for statements Postgres refuses to run in a transaction:

- `CREATE INDEX CONCURRENTLY` / `DROP INDEX CONCURRENTLY`
- `ALTER TYPE ... ADD VALUE` (on older Postgres versions)
- `VACUUM`, `REINDEX CONCURRENTLY`

Consequences to respect:

- A non-transactional statement gets **its own file and its own revision**. Never
  bundle a concurrent index with other changes.
- Name those files for what they are: `0003_add_email_index_concurrently.up.sql`.
- The `.down.sql` for a concurrent index is also concurrent, and also alone.

## Enums

Postgres enum labels are `UPPER_SNAKE` and match the Python `StrEnum` members
exactly. The type is `pb_` plus the class name in snake_case — `TextType` →
`pb_text_type`.

```sql
CREATE TYPE pb_text_type AS ENUM ('BLOG_POST', 'NEWSLETTER');
```

Adding a member is `ALTER TYPE pb_text_type ADD VALUE 'NEWSLETTER'`, in the same
commit as the Python change. Removing one is not supported by Postgres — it requires
creating a new type, migrating the column, and dropping the old, which is three
statements and a transactional file.

## Data migrations

Backfills go in their own `.up.sql` file, separate from the DDL that made the column
exist, so a slow backfill can be rerun or skipped independently. The `.down.sql` for
a backfill is usually a comment explaining that the data change is not reversible.

Batch anything touching a large table; a single `UPDATE` over every row holds locks
for the duration.

## If `migration_runner.py` does not exist yet

Create it from `reference/migration_runner.py` in this skill. It requires
`sqlparse` — add it to the project dependencies with `uv add sqlparse`. Splitting SQL
on `;` is not acceptable; semicolons appear inside string literals, comments, and
function bodies.

`migrations/` imports nothing from `apps/` or `libs/`, and nothing imports from
`migrations/`.
